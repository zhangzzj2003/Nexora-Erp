# 单据审批、关联查询与可选批次实施清单

本文件是实施约束与验收清单，所有未勾选项均为待实现，不能表述为已交付。

## 当前实施状态

需求分支正在实施，尚未完成整体验收或部署。

已加入第 89 版数据库的审批模板、模板变更、审批实例、追加事件和单据作者表；模板范围与 29 类编号清单一致。共用事务服务支持独立审批、一至五步模板、步骤角色、内容摘要、递增版本、驳回、撤回、重新提交和执行留痕。管理员也不能自审，多步审批不能由同一个人重复批准。审批事件、模板变更和作者记录禁止修改或删除；迁移不会为历史单据伪造审批记录。

模板接口为 `GET /api/v1/system/document-approvals`、`GET /{document_type}` 和管理员专用 `PUT /{document_type}`；输入仅包含版本及步骤名称、可选职务，审核权限始终由服务端固定目录决定。系统“连接与服务”中已加入管理员配置组件，使用 Pinia 保存草稿和版本，保存冲突保留输入，换实例、账号或授权变化失效旧请求。

**业务入口尚未全部接入共用审批服务。当前已接入销售报价、售后单、采购申请、其他入库、采购订单、采购收货、采购入库、采购退货、仓库出库、调拨、盘点、库存调整、销售订单、销售出库、销售退货、生产工单、领料、退料和完工的送审、独立步骤、驳回、撤回与执行；适用冲销的这十二类库存单据均支持独立冲销审批，不代表 29 类单据已全部审批后执行。** 收付款与成本结算的待审状态、其余六类既有审批兼容、生产关联查询及全范围验收仍按下列清单继续实施。

## 已接入：其他入库

- `GET /api/v1/system/document-approvals/WarehouseInbound/{id}?intent=execute|reverse` 按 `other_inbound.view` 读取进度、送审正文摘要和完整人员/时间/意见记录，审批步骤名称使用当次固定模板。
- `POST /{id}/submit|approve|reject|withdraw` 只接受严格整数 `version`、`intent`、`reason`；正文和作者由服务端查询。入库送审沿用 `other_inbound.create`，冲销送审沿用 `other_inbound.reverse`，审核需新增独立权限 `other_inbound.review`。
- 未完成最后一步批准时，两种 `/warehouse-inbounds/{id}/post` 调用都返回 409。批准后可以普通确认入库，也可选择登记实物批次；批次数量与日期仍由原领域校验。审核固定的是业务数量和来源正文，仓库执行时另记实际实物证据。
- 冲销原因单独送审、批准；执行使用同一固定原因和原分配，在原写事务内重核库存。原入库批准不能当作冲销批准；重复执行、已处理动作、改变正文、错误数量均不会部分写入。
- 正在审批或已批准时须先撤回才能取消。历史已执行记录原样保留，不追加虚构批准。
- 桌面端共用审批弹窗和 Pinia 意见草稿已接入其他入库；换实例/账号时清除，失败或同实例断线保留意见，刷新版本前不能继续操作。

## 已接入：采购申请与分批转单

- `PurchaseRequest` 共用带版本审批入口，支持一至五步独立审核、核准、批准。最后一步才将原申请投影为已批准；编制、编辑、提交和原 MRP/维护来源作者均不能自审。旧无版本提交、批准、驳回接口保留原权限校验后返回 409。
- 正文固定参考号、采购说明、行物料、数量与来源，不包含动态已转量。批准后的第一次转单与申请执行事件同事务提交，后续按同一固定授权继续分批转换；每次仍在原写锁内重算剩余需求，取消订单草稿才释放额度。失败整体回滚子订单、行关联和执行事件。
- 每张派生采购订单保持未送审草稿，单独审核供应商、数量和价格；原申请创建、编辑、提交及来源方案作者不能审核订单。不能将申请批准等同于订单批准。
- 待审或批准申请须先撤回才可取消；原 MRP 和维护申请禁止直接编辑，继续按原来源规则更正。旧已批准申请的剩余需求须重新独立审批，首次事件保存原提交/审核人员、时间与意见；已关联历史订单、数量及编号不改写；即使新审批驳回，也不能删除旧订单引用的申请行。全部转完的旧申请只作历史查询，不补造批准。
- 桌面申请列表使用共用审批弹窗，移除旧无版本审核动作。无统一批准不能转单，首次执行后合法剩余可继续转单；弹窗已打开时撤回或权限变化也不能提交。
- 已补充真实接口与实际编译 Vue 页面测试，覆盖多步状态、自审与编辑人员、并发拆单额度、正文变化、执行事件故障回滚、旧部分转单及 MRP/维护来源恢复。
- 隔离数据库的实际页面已验证申请送审、其他人员独立批准，并拆成 4 个与 6 个的两张采购订单草稿。申请剩余量归零，执行事件只记录一次，两张订单均未送审；明暗主题及历史滚动检查无控制台错误，未更改已安装服务或业务数据库。

## 已接入：采购订单、收货与入库

- 三类分别使用 `PurchaseOrder` / `PurchaseGoodsReceipt` / `Receipt` 读取、送审、批准、驳回及撤回；查看权限与原列表一致，审核使用各自独立权限。管理员也不能自审，送审固定供应商、仓库、参考号、数量、价格及来源行关联；收货还固定拒收数量与原因。
- 采购订单批准后才可确认，收货批准后才可生成采购入库草稿。生成的入库单未送审，不能直接确认；转单执行人员和原收货建单人员都不能审核派生入库单。
- 原数量/订单状态校验仍在执行事务内重算；不同草稿分别批准后，也不能超量收货或入库。并发撤回与执行只有一个成功，错误批次和业务写后故障整体回滚，保留批准状态以便修正执行输入重试。
- 桌面采购三页面提供审批进度、固定正文及历史记录；批准后才显示确认动作，普通采购入库不要求批次，可选择登记实际实物证据。正在审批或已批准的订单、收货草稿须先撤回才能取消。
- 主进程校验业务列表和执行响应中的完整审批进度及独立冲销进度；旧响应缺少审批字段时界面不开放执行，残缺的“已批准”响应被拒绝。
- 采购入库冲销使用单独的 `reverse` 审批与固定原因，执行重核原库存、退货依赖和原实物分配；原入库批准不可复用。历史已执行记录仍不补造批准。

## 已接入：采购退货与仓库出库

- 退货使用 `PurchaseReturn` 送审，批准固定原入库、供应商、仓库、逐行退货数量、原因及原采购价格关联；原 `/{id}/submit` 现在是批准后的转单动作，只生成未送审仓库出库草稿并记录父单执行。
- 仓库出库使用 `WarehouseOutbound` 独立审批，送审沿用 `other_outbound.create`，审核使用独立 `other_outbound.review`，执行仍使用原权限。出库摘要不暴露采购价格；原退货建单与转单人员均不能审核子单。维护、售后派生耗材出库同样记录原方案编制人员并独立批准。
- 旧 `/purchase-returns/{id}/post` 保留固定路径，但不再自动补建并确认子单；必须先批准退货、转单、再批准仓库出库。父单固定正文、父子数量对应、可退量、库存和可选实际批次在同一库存事务内重核，执行失败仍保留批准且不记部分流水。
- 旧库尚未执行的待出库子单保留原 ID；退货重新批准后可复用对应草稿，子单若正在审批或已批准须先撤回，再记录转单人员并重新送审。历史已执行记录不补造审批。
- 维护、售后旧待出库草稿在送审时从原方案及原编制审计读取作者范围，不依赖新作者表已经存在记录；作者与来源关联纳入服务端固定快照，客户端不能提交或替换作者名单。
- 桌面退货页提供审批与“生成出库草稿”，仓库页提供批准后的普通“确认出库”和可选实物批次。取消退货时父子任一待审或批准均须先撤回；冲销从原退货另行审批，其他用途出库从原出库单另行审批固定原因，沿原分配冲销。
- 采购退货冲销后，仓库出库保留原确认记录，并以独立的父退货冲销关联显示“采购退货已冲销”，不把父冲销 ID 当作其他出库冲销 ID。
- 本阶段实际页面已验证不同人员完成退货批准、转草稿、出库送审、独立批准和普通确认；未指定批次时不生成实物分配。另行提交固定原因、独立批准并执行退货冲销后，追加恢复流水且关联页面状态一致。已检查明暗主题及 760×900 窄窗口的审批历史；这些证据只覆盖当前接入范围，不能替代剩余单据验收。

## 已接入：调拨、盘点与库存调整

- `Transfer`、`Stocktake`、`StockAdjustment` 各自使用统一入口送审、分步批准、驳回和撤回；审核沿用或使用 `transfer.review` / `stocktake.review` / `adjustment.review`，执行权限与原业务一致。冲销另行提交固定原因，不复用原单批准。
- 调拨固定来源仓、目标仓及逐行数量，执行仍原子追加两仓流水；盘点固定建单账面量、实盘量和流水检查点，批准后仍检查期间流水，净额相抵也不会掩盖期间业务。
- 库存调整的原状态随统一审批投影，中间批准步骤仍保持待审批；全部步骤完成后才允许仓库确认。升级前待执行调整单须重新送审，第一次送审单独归档原提交、审核人员、时间与意见，界面明确标为历史核对资料，不冒充新审批步骤。已执行旧单据不补造批准；原提交人员也不能审核旧单冲销。
- 原无版本调整 `submit` / `approve` / `reject` 返回 409，提示使用统一入口，防止旧客户端跳过模板或冲突检查。处于待审或批准时，盘点、调整须先撤回才能取消。
- 三个页面提供批准后的普通确认及可选实物批次，批次弹窗打开后撤回审批仍会阻止提交；冲销执行重新读取已批准原因。无批次记录明确显示普通确认，不推断采购来源。
- 单元及真实接口验证覆盖独立多步、普通确认、另行冲销、并发仅一次、业务流水故障回滚、正文与盘点检查点变化、旧调整记录保留、原状态同步及旧入口拦截；既有数量、余额和逐批冲销断言继续运行。实际页面已验证三类普通确认、旧调整重新送审、两位不同人员分别核准与批准，以及盘点固定原因另行批准后冲销。已核对库存与审批记录均已执行、无批次分配及明暗主题下 760×900 的历史滚动显示；未检测到页面控制台错误。

- 转单在同一 ORM 事务生成独立未送审销售订单、更新原商机及报价、追加双方原审计和审批执行事件，任一失败整体回滚。旧已批准但未转换报价须重新取得统一批准，原人员、时间及意见归档为历史核对；已转换旧记录不补造审批。
- 桌面共用审批弹窗保留报价操作依据；审批刷新同时读取 CRM 独立列表与当前详情，保留未保存表单。换实例/账号、关闭详情及撤权不能恢复迟到响应，已打开转单弹窗也不能使用撤回或改版后的旧批准。
- 已验证报价多步、固定名称与附件、旧入口拦截、客户越权、最大正文、并发和事件写后回滚；实际页面完成送审、另一人员批准、带客户接受依据转单及子订单另行送审批准。明暗主题 760×900 下审批历史可滚动、底部操作固定，页面控制台无错误；全范围验收仍未完成。

- 刷新审批记录时同步原业务列表，其他客户端批准后无需再次刷新列表；已完成冲销仍可查看其独立批准与执行记录。

## 已接入：生产工单、领料、退料与完工

- `WorkOrder` / `MaterialIssue` / `MaterialReturn` / `ProductionCompletion` 分别使用共用版本接口送审、分步批准、驳回及撤回，审核权限分别为 `work_order.review` / `material_issue.review` / `material_return.review` / `production_completion.review`；执行与查看权限保持原领域边界。
- 工单固定 BOM 版本、产量、目标仓库和需料快照，批准后才能下达。MRP 转单与不合格品返工生成的工单不继承上游批准，并从原方案创建、提交、编辑、转单审计恢复原作者，旧草稿也不能绕过独立审核。返工工单正在审批或已批准时，上游处置更正须先撤回子单审批，不能静默取消子单。
- 领料固定工单、来源仓、行关联与数量；退料固定原领料、原因与行数量。执行仍核对净领料、工单产量、原领料可退量、仓库及可选批次余额，不能因批准而超领或超退。
- 完工草稿先登记质检，检验后的合格/不合格数量与说明固定在送审正文中；质检人员属于编制人员，不能自审。整批不合格批准后仍可确认报工，但不生成合格库存或实物批次。批准后确认仍重核目标产量与净领料。
- 三类库存操作提供普通确认及可选实物批次；普通确认不提交批次载荷、不虚构采购来源。审批撤回后已打开的可选批次弹窗不能继续确认。领料、退料与完工各自另行审批固定冲销原因，继续遵守期间、成本结算、下游依赖和原证据规则。
- 在同一 ORM 写事务内执行与追加审批事件，失败整体回滚。页面显示本单独立进度，待审或批准的草稿须先撤回再取消，已执行/冲销记录仍可查询完整人员、时间和意见。
- 新增真实接口回归覆盖四类多步审批、并发仅一次、正文变更、执行事件故障回滚、质检人自审与 MRP/返工作者恢复；实际编译 Vue 页面测试覆盖普通调用、待审保护、质检前置、零合格量、撤回后批次弹窗失效和固定冲销原因。全范围 29 类、资金待审状态和生产关联查询仍待后续实施。
- 隔离数据库的实际页面已验证工单批准下达、领料与退料分别批准后普通确认、完工质检后独立批准普通入库，以及完工、退料、领料依次另行批准冲销。最后原材料库存恢复、成品归零、工单净领料归零，三类均没有生成实物批次分配。已检查明暗主题、760×900 历史滚动与固定操作区，没有控制台错误；未更改已安装服务或业务数据库。

## 目标

- 普通业务操作不强制实物批次登记；普通表示按单据数量处理，绝不表示跳过审批。
- 29 类核心单据与独立资金记录均具有服务端业务单号；已有编号规则、历史编号和内部 ID 继续保留。
- 各类单据默认一次独立审批后执行，按单据类型提供审批步骤配置；已有审批、质检、验收与业务限制继续保留。
- 生产工单、完工单提供关联单据查询，展示 BOM 版本、需求快照、实际领退料和完工记录。
- 只有固定批次分配证据能证明实际领料来源；同物料采购记录只能作为排查参考。
- 工单层面的领料来源不能被标为某台产品或某次分批完工的确定耗用来源。

## 技术设计草案

以下是全范围实施约束；审批基础结构已实现，业务接入范围仍以前述已接入清单为准。数据结构、接口及迁移必须以正式代码与验收结果为准。

1. 数据库保存按单据类型划分的审批模板；模板默认一个独立批准步骤，配置变更使用版本检查。送审时固定本次模板，不让之后的设置变更静默改变已送审流程。
2. 审批实例记录单据类型、单据 ID、操作意图、内容版本和摘要；事件表追加记录提交、步骤批准、驳回、撤回及执行，不能覆盖以前的决定。
3. 业务执行在原 ORM 写事务内重核批准状态、内容和原有业务条件。不能只在路由外先读审批，再释放锁后执行，否则会留下并发撤回和执行的窗口。
4. 现有十类审批接入步骤配置时仍保留其领域校验、作者记录、固定快照及独立审核或验收；不能叠加第二套互不关联的批准状态。
5. 各类单据按实际生效点接入：订单确认、工单下达、收货转入库、退货转出库、仓库流水确认等都必须重核批准。
6. 收付款、分户收付款、订单核销及生产成本结算需要明确的待审状态。所有余额、成本、期间锁、来源凭证与关联查询只累计已执行记录；执行时重新校验余额或成本来源，避免批准后依据变化仍错误生效。
7. 审批和执行通过受限 IPC 固定操作暴露；共享类型及主进程响应校验同步维护。新增共享界面状态使用 Pinia，复用现有 Naive UI 封装和单据弹窗。
8. 单据查询先返回生产范围内的 BOM/需求快照、领退料、完工状态及冲销关系；采购来源额外遵守当前库存查看权限，不返回不必要的价格或资金数据。
9. 入库来源确认使用实际领料分配的批次及其原始库存流水 ID。不得用供应商批号字符串、FIFO、平均成本或同名物料推断确定来源；跨供应商同批号不能合并证据。
10. 缺少固定批次分配时，采购记录单独展示为同物料排查参考，并说明范围、时间和数量限制；工单涉及物料不等于该批成品确定耗用物料。

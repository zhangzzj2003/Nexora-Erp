# 历史原单与现有订单核销

单公司、人民币条件下，历史贷方原单可抵现有销售或采购订单的待结款，订单退货形成的贷方也可抵历史待结原单。历史分户方案须已确认启用；双方必须属于同一应收/应付类别、实际客户/供应商、控制科目及完整辅助组合。不同科目、部门、项目之间的转账仍未提供。

## 归属依据与额度

订单归属来自实际已过账的业务来源凭证、绑定时的科目及分录辅助快照，不套用当前通用映射。销售/采购业务及已执行资金的非零来源须全部可核对，缺价、成本缺口、未过账、已冲销凭证、经济指纹变化、启用日前或未来来源都会阻止核销。新来源凭证保存用途分录位置；旧凭证只接受原服务端固定摘要、科目、金额及实际往来身份的唯一精确匹配，缺少证据时不猜测、不回填。

同一订单可以具有多个科目或辅助组合。每次核销选取与历史原单完全一致的组合，金额同时受历史原单余额、订单整体余额和该组合余额约束；任一项不足都拒绝。保存的凭证依据标明实际分配订单，选择页面显示三项余额和最小额度。草稿与批准不预占额度，执行时在 ORM 写事务内重算，两个批准草稿竞争同一剩余额度只允许额度内的执行成功。

旧订单间核销没有科目和辅助字段。仅当整条相连订单链的所有来源均可证明为唯一相同组合时，才重放其额度归属，并固定整条链的实际凭证与核销依据。缺口传播到所有相连订单；同对象但跨科目或辅助的旧事实仍保留，不能用当前映射补造归属。旧核销全部反向执行后，其净影响及依赖解除。已有有效历史与订单核销时，影响该相连链的新订单间核销也须具有唯一同组合归属。

## 接口、权限与审批

基路径为 `/api/v1/finance/subledger-order-settlements`。

| 接口 | 行为 |
| --- | --- |
| GET 基路径 | 返回核销草稿、执行、取消及反向记录和固定依据 |
| GET `/options` | 返回有效方案原单、订单整体及分组合余额、凭证依据和阻止原因 |
| POST 基路径 | 保存草稿：`opening_line_id`、`order_id`、`direction`、`amount`、`reference`、`reason` |
| POST `/{id}/post` | 完整批准后，携带业务 `version` 与必填依据执行 |
| POST `/{id}/cancel` | 取消草稿；待审或批准时须先撤回，保留单号并释放参考号 |
| POST `/{id}/reverse` | 保存原事实的等额负金额反向草稿，重新批准后执行 |

`direction` 为 `historical_credit`（历史贷方抵订单）或 `order_credit`（订单贷方抵历史）。普通金额为正数、最多两位小数；ID 为严格正整数，参考号最多一百字，依据最多二百字。接口不接受客户端指定科目、辅助归属、状态或执行人员。

所有接口及审批读取均要求独立 `subledger_order_settlement.view`，另按动作要求 `finance.record` 或 `finance.reverse`；审核步骤使用 `finance.review|verify|approve`。默认仅补给已有财务查看权的内置管理员和财务，自定义角色须明确授权。旧历史查看权不会获得订单和凭证依据，旧资金查看权也不会自动获得历史原单信息。

统一审批类型为 `SubledgerOrderSettlement`，路径 `/api/v1/system/document-approvals/SubledgerOrderSettlement/{id}`。固定原单、真实订单身份、科目及完整辅助、金额、方向、参考号、原记录和当前凭证依据状态；依据变化使已批准内容失效。执行与审批事件同事务提交，失败整体回滚。操作弹窗同时固定业务及审批版本，实例、证书、账号、角色或权限变化使旧弹窗及排队操作失效。

## 余额、撤销与归档

执行历史贷方抵订单时，历史原单 `order_offset_amount` 为负，订单 `historical_debt_covered_amount` 增加；反方向时，历史原单核销净额为正，订单 `historical_credit_used_amount` 增加。历史总核销净额及订单总抵扣额均包含这些事实，后续收付款按最新未结余额限额。两个同组合端点净额为零，不生成资金、库存流水、总账分录或新的业务凭证来源。

反向必须沿原科目、完整辅助、订单及凭证依据，金额精确相反；不套用普通新核销额度。原记录不改写，不允许重复有效反向或反向再反向；取消反向草稿后可重新申请并取得新号。原执行日期或当前日期锁期时不能更正，须按原规则倒序重开。有效已执行核销所依赖的直接或间接凭证不能冲销；创建冲销草稿和冲销过账两处都检查，须先批准执行反向核销。存在未取消草稿或执行历史的分户期初不能撤销。

余额按实际执行 UTC 日期累计，期间结账另固定 `subledger_order_settlements` 和双边余额；旧归档 JSON 原样保留，不补造历史证据。

## 桌面与升级

桌面入口为“财务管理 → 分户期初 → 历史与订单核销”。页面先读取最新依据，按方向筛选原单，再仅列出完全匹配且有相反余额的订单；提供保存、凭证依据、统一审批、执行、取消和反向草稿入口。订单缺少凭证或归属不明时展示具体原因；失败保留输入，断线暂停写入，明暗主题与窄窗沿用现有组件及表内滚动。路由仍要求 `subledger_opening.view`，新模式另要求专属查看权；只授专属查看权的角色可使用统一审批查询，但不会因此取得分户页面权限。

数据库 v97 新增 `SubledgerOrderSettlement` 静态 ORM 表、索引、默认审批模板和权限，编号 `LSDDHX` / `SOL`；当前为 197 张模型表、31 类编号及审批单据。迁移不改既有金额、凭证、核销、编号或归档，失败原子回滚并可重试。客户端与后端须一起升级。

测试覆盖四种类别及方向、科目和完整辅助、多个组合额度、旧凭证兼容、旧订单链依赖、独立权限、并发、批准后依据变化、资金限额、重复执行、追加反向、凭证保护、期间归档、审计故障和 v96 升级回滚。实际页面验收仅使用隔离临时数据库及明确标注的示例数据，不替代已安装服务升级、真实凭证和业务方期初验收。

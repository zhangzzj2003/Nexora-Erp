# 销售订单合同正文与修订证据

数据库第 81 版新增 `SalesOrderContractRevision` 声明式 ORM 模型。销售订单页可按原有客户归属查看订单级合同全文与所有历史版本；旧订单未登记时明确显示空历史，不推断其合同内容。

拥有销售订单确认与查看权限的人员，可在未取消订单上登记正文、客户确认依据及登记或修订原因。每次保存追加递增版本、操作人和时间；客户端提交已读取的版本，若期间已有新版本则返回冲突，要求重新核对。相同正文与相同客户确认依据不得重复登记。正文最长 20,000 字，客户确认依据最长 400 字，原因最长 200 字；空白输入、额外字段和无权查看的客户订单由服务端拒绝。取消订单保留历史但不再接受新版本。

第 82 版新增合同版本附件及撤销证据两张 ORM 表。销售订单页可在每个合同版本下上传、查看和保存 PDF、PNG、JPEG 原件，单文件不超过 5 MiB，每版最多 10 个有效文件。上传须有 `sales.view` 与 `sales_order.confirm`，查看与保存须有 `sales.view`，且全部沿用订单的客户可见范围。取消订单后只能查看与保存历史。相同版本的有效文件按 SHA-256 去重；误传通过追加撤销记录更正，原文件、摘要、依据、人员和时间仍可核对。下载时服务端与桌面端分别核对长度、摘要和文件格式，桌面端切换会话后不继续保存旧文件。附件按指定正文版本归档，后补上传的实际时间仍如实显示，不追认为版本建立时已存在。

正文及附件是人工登记的合同证据，不能证明签署文件或签名真实，也不构成电子签名或法定合同审查。修订与附件操作不会重写订单明细、金额、保修天数、已确认出库、售后来源快照、应收或总账；涉及价格和保修条款的变更仍需按相应单据流程另行办理。系统不自动从合同正文或附件提取条款或判定售后责任。签署真实性验证与更严格的合同审批尚未实现。

接口为 `GET /api/v1/sales-orders/{id}/contract` 与 `POST /api/v1/sales-orders/{id}/contract`。写入参数是 `expected_version`、`body`、`acceptance_reference`、`reason`；返回当前版本及按版本倒序的完整历史。两者只通过 ORM 会话访问业务数据，迁移建表使用 SQLite 结构操作。

版本附件接口为 `GET/POST /api/v1/sales-orders/{id}/contract/revisions/{revision_id}/attachments`、`GET /api/v1/sales-orders/{id}/contract/revisions/{revision_id}/attachments/{attachment_id}` 与同一附件路径的 `POST /reverse`。上传参数为文件名、Base64 内容和依据；撤销须填写原因。业务读写使用 ORM 会话，迁移和备份保留必要的底层 SQLite 操作。

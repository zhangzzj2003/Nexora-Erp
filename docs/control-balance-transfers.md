# 往来余额转账

数据库 v101、单公司、人民币。历史原单和现有订单可按真实控制科目及完整客户/供应商、部门、项目组合办理余额转账。使用 SQLAlchemy 声明式模型及 ORM 会话，金额用 Decimal 精确计算；不登记新的银行资金，不改写原订单、历史分户正文或原凭证。

## 两种用途

- **原单余额重分类**：同一历史原单或订单的借方/贷方余额，移到该原单的另一控制科目或完整辅助组合。可转入已有组合或建立新组合，原单未结合计保持不变。
- **跨原单贷方分配**：同一实际客户或供应商的贷方组合，抵扣另一历史原单或订单的借方组合。支持历史→历史、历史→订单、订单→历史、订单→订单，分别核对两侧实际额度。双方组合须不同；同科目同组合的原有核销仍使用原入口。

必须同应收/应付类别和同一实际往来身份，不能将客户和供应商或两个往来对象的余额抵消。完整组合以类别和编号确定，显示名称及辅助顺序不改变身份。目标控制科目须启用，历史分户存在时限于该类别登记的控制范围；未启用历史分户时，以已证明的业务来源和当前用途映射限定范围。部门、项目按目标科目辅助规则及业务日期校验。草稿保存的两侧科目、全部辅助、真实来源、余额与指纹由服务端冻结，客户端不能指定已执行状态或替换实际对象。

例如同一客户的历史贷方原单在 AR/项目甲有 30 元，另一订单在 AR2/项目乙尚欠 20 元，可分配最多 20 元。转账过账后前者为 -10 元，后者为 0 元，公司未结合计和银行资金均不变。对供应商应付使用相同的未结正负语义，凭证借贷方向按负债用途反转。

## 真实来源与日期

历史组合从当前已确认分户方案、原单及资金/核销事实投影；订单组合从已过账业务来源凭证的真实往来用途分录恢复，不套用当前通用映射猜测旧归属。订单来源须与固定经济指纹和实际分录相符；未定价、未过账、错误往来或无法还原旧核销链的原单显示依据缺口并阻止转账。

没有历史分户方案时，可使用已配置业务凭证启用日后的订单来源。日期采用 UTC，须在开放期间内、不晚于当日，并不早于两侧已固定的来源事实。额度按实际组合核对：重分类不超过该组余额绝对值，跨原单分配不超过来源可用贷方和目标未结借方中的较小值。不同组合的正负抵消不能用原单净额替代单组额度。

## 两次独立批准与原子过账

1. 建立 `ControlBalanceTransfer` 草稿。保存和批准都不改变余额，也不预占额度。
2. 转账经一至五步统一审批批准。固定两侧完整组合、原来源、金额方向、日期、参考号和依据，沿当前步骤角色按钮权限办理。
3. 从已批准转账生成固定的两条凭证分录。日期和币种沿转账，科目、完整辅助及借贷金额不可编辑；生成仍不生效转账。
4. `Journal` 独立送审及批准，真正过账时再核对两次当前批准、两侧最新来源指纹、额度、日期、期间和操作权限。
5. 凭证过账、转账生效、两张审批执行事件和转账审计在同一 ORM 写事务提交。并发竞争或审计失败整体回滚，不能留下单边余额或单独已过账凭证。

父转账撤回后，已有凭证即使曾批准也不能过账。未过账凭证须先撤回其待审/批准审批，再取消；取消留存原凭证，允许从仍有效的批准转账重新生成。取消转账草稿须先撤回父审批，并没有有效未取消的关联凭证；服务端在同一事务中重新核对创建/更正权限和双方原单查看权限，拒绝时不改变草稿或审计。通用凭证编辑和冲销不能绕过该转账流程。

## 后续收付款

历史原单或订单一旦办理过组合转账，新收付款必须显式选择该原单的真实控制科目和完整辅助。保存资金草稿固定此组合，批准后真正执行时再次核对当前组合余额；退款选择实际贷方组合，收/付款选择实际借方组合。一个原单合计为零但内部仍有正负组合时，可分别按对应组办理。

资金执行即按实际组合扣除业务可用额度；尚未生成、绑定草稿或尚未过账的资金凭证不能再次释放这笔额度。待过账资金会阻止新的余额转账及更正，须先补齐真实总账依据。资金来源凭证使用固定的实际往来科目和辅助，不能用后来修订的通用映射改回旧组合。

v101 前资金的新增组合列为 null，旧审批正文和旧来源经济指纹保持原样。新功能不反向补造旧资金组合。已有只保存原单身份的核销不能在存在有效新转账的原单上继续办理，避免丢失实际归属；新增完整组合分配使用本模块。

## 追加式更正与截止日

已生效转账保留原记录和原凭证。错误另建等额反向转账草稿及反向凭证，两者分别重新批准，真正过账后恢复归属。反向日期不得早于原转账；原单锁定、关闭期间和下游事实均受保护。依赖原转账的后续转账、资金和对应凭证须先倒序更正；不能通用冲销来源凭证或原转账凭证来破坏已生效依据。

截止日组合余额按原转账和反向转账各自的业务日期重放。次日更正不会消除前一天的转账事实，已释放的业务凭证绑定按当时的真实过账及更正日期恢复。历史原单余额及现有订单余额另列组合转账调整额；同原单重分类净额为零，跨原单分配分别调整两侧原单总额。期间证据固定截止范围内转账、完整组合与来源，不把其他无关订单的依据缺口当成本模块的结账阻止项。

## 接口、权限与升级

桌面入口为 `/workspace/control-balance-transfers`，独立 `control_transfer.view` 查看权限；历史原单另需 `subledger_opening.view`，订单另需 `finance.view`。创建、审核、核准、批准、办理和更正分别使用 `control_transfer.create/review/verify/approve/post/reverse`。生成凭证另需 `journal.create`，查看及过账另需 `journal.view/post`；取消关联凭证另需 `journal.cancel` 和父转账创建/更正权限。资金组合查询只依赖 `finance.record` 及原有原单查看权限，不要求新增转账查看权限。客户端撤权、切换实例/证书或断线清除旧读取结果并拒绝排队写入。

| 接口 | 用途 |
| --- | --- |
| `GET /api/v1/finance/control-transfers`、`/{id}`、`/{id}/changes` | 按权限裁剪记录、固定来源详情与不可覆盖审计 |
| `GET /options`、`/balances?to_date=YYYY-MM-DD` | 当前依据或指定 UTC 截止日完整组合余额 |
| `GET /funds-options?kind=…&source_type=…&source_id=…` | 实际资金组合及是否必须选择 |
| `POST /api/v1/finance/control-transfers` | 保存不占额度的草稿 |
| `POST /{id}/generate`、`/{id}/reverse`、`/{id}/cancel` | 生成固定凭证、建立反向草稿、取消草稿，均保留真实业务版本及必填依据 |

v101 原子新增 `control_balance_transfers`、`control_balance_transfer_changes`，订单资金与历史资金各加可空组合列；新增第 32 类编号与审批单据，前缀 `WLYEZZ/CBT`，共 202 张静态 ORM 模型表。只给原已有财务查看权限的内置管理员/财务角色分配新增权限，不扩大自定义角色。迁移失败整体回滚，可重试；保留历史凭证、审批 JSON、来源指纹和固定归档。服务端和桌面端均需升级。

当前不包含跨公司、多币种、客户与供应商相互抵销、外部债权转让协议、税务处理、银行自动支付或运行中补导。浏览器隔离数据和测试通过不等同于真实业务资料或银行凭据已核实。
